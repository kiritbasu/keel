- **KEEL-227** A daemon too old to check for updates says nothing, which is when you most need telling `p1` · updates, ui

  Found immediately after KEEL-225 landed, by looking at the real daemon rather than a test.
  
  `/api/health` on the live daemon reports `version: 0.1.0` and **no `staged_version` field at all** — it is a binary from before the updater existed. So it has never checked, never staged, and the footer correctly offers nothing. `keel --version` on the PATH also reports 0.1.0, while the 0.1.2 install went to `CARGO_HOME`, which is not on the PATH by default. The same multiple-binaries trap KEEL-221 hit.
  
  The design flaw this exposes: **"an update is available" is inferred entirely from the daemon having staged one.** That works from 0.1.2 onward and fails silently for everyone before it, which is the population that most needs telling. It also fails for a 0.1.2 daemon that cannot reach the network, and for one with `KEEL_AUTO_UPDATE=0` — in both cases the interface shows a version and implies everything is fine.
  
  Options worth weighing, not settled here:
  
  - **Absence is information.** If health omits `staged_version` the daemon is older than 0.1.2, and the interface knows that without asking anything. It could say "this daemon is too old to check for updates" from the missing field alone. Costs nothing and needs no request.
  - **Compare against a known-latest.** More useful and more expensive: something has to know what the latest release is, and if the daemon cannot check then the only other candidate is the page, which reopens the question of the interface making outbound requests (que about the interface and the internet).
  - **Say when the last check happened.** A version with no "checked at" beside it cannot be distinguished from a version whose check is failing quietly.
  
  Also worth fixing while here: the interface should say *which* binary the daemon is, not only its version. KB has at least two `keel` binaries and the one on his PATH is not the one he installed.

- **KEEL-222** There is no way to uninstall Keel, and the install receipt is a single global file `p2` · phase10, release, cli

  Asked whether there is an uninstall command. There is not, and the gap is wider than a missing convenience.
  
  `dist`'s shell installer normally gets uninstall from `axoupdater`, and `install-updater = false` turns that off — correctly, for the reason in the config: a second updater that knows nothing about the store would walk straight through the schema guard `keel update` exists to enforce. But nothing replaced the half that was worth keeping.
  
  ## What an install actually leaves
  
  Measured on this machine rather than listed from the installer:
  
  - `~/.cargo/bin/keel` and `keel-daemon`, or `~/.local/bin/` when `plugin/install.sh` did it
  - `~/.keel` — the store, which is the one thing that must never go without being asked
  - `~/.config/keel/keel-receipt.json`
  - `~/Library/LaunchAgents/sh.keel.daemon.plist`, loaded
  - `~/.claude/skills/keel/` — the skill, the shim, and two forwarders
  - a `. "$HOME/.cargo/env"` line in `~/.zshenv`, `~/.zshrc` and `~/.profile`
  
  Seven paths across four directories, plus three shell profiles. Removing the binaries without unloading the agent leaves launchd restarting something that is gone, every few seconds, and the failure surfaces as a log nobody is reading.
  
  ## The receipt is a single global file, and it is already wrong
  
  `~/.config/keel/keel-receipt.json` is one path with no scoping by install prefix, so **any** install overwrites it. It currently reads:
  
  ```
  "install_prefix": "/tmp/keel-011-test/cargo"
  ```
  
  which is a scratch directory used to verify 0.1.1 and deleted immediately afterwards. The real binaries are in `~/.local/bin`. So the only machine-readable record of where Keel is installed points at nothing, and it took one test install to get there.
  
  That matters beyond tidiness because **KEEL-203's updater will want to read this**. An updater that trusts a receipt naming a deleted prefix either fails confusingly or, worse, installs somewhere nobody is looking while reporting success — the shape this project keeps meeting.
  
  ## What to build
  
  `keel uninstall`, with the properties the rest of the CLI already has:
  
  - Names every path before touching it, and removes nothing silently.
  - **Keeps the store by default.** `~/.keel` is the user's data and the only irreplaceable thing here; removing it needs an explicit second flag and a sentence saying what is being destroyed.
  - Stops and unloads the service before removing the binary it points at, in that order.
  - Leaves the shell profiles alone but says which lines are now dead, because editing somebody's `.zshrc` is the thing `install.sh` already refuses to do and the reasoning has not changed.
  - Works when the receipt is wrong, since it demonstrably can be. Find the binaries rather than trusting the file.
  
  Worth pairing with a fix for the receipt itself — either scope it by prefix, or have `keel` write its own record on first run and stop depending on the installer's.
  
  This blocks repeatable install testing: KEEL-221 wants the three-command flow run on a second Mac, and without an uninstall there is no way to get that machine back to a clean state to try it twice.

- **KEEL-220** Put embeddings behind a feature so Intel macOS and Linux can be built at all `p2` · phase10, release, build

  Comes out of the first release run, where `aarch64-apple-darwin` built and the other two did not. Both failures were `ort-sys` and neither is fixable by changing the build:
  
  - `x86_64-apple-darwin` — no prebuilt ONNX Runtime exists for the target.
  - `x86_64-unknown-linux-gnu` — the prebuilt wants glibc 2.38 and libstdc++ 13, against a runner deliberately pinned to 2.35 to keep the floor low for older distributions.
  
  `ort` downloads a prebuilt static library rather than compiling one, so the platforms Keel can ship to are the platforms someone else chose to build ONNX for. Nothing about Keel's own code is in the way.
  
  **This reopens a settled position and should be argued rather than assumed.** No workspace crate declares a feature, and Phase 9 removed the last one on the grounds that the `bundled` chain existed only to let someone link a system DuckDB and changed nothing that mattered. That reasoning does not transfer. A feature deciding whether a platform can be *built at all* is a different kind of thing from one that changes which copy of a library gets linked, and this one has a user-visible meaning that is already documented: keyword search works without embeddings, so a build without them is a supported configuration rather than a broken one.
  
  What it likely touches, from a read of the tree rather than a guess:
  
  - `keel-embed` is the only crate that constructs a `FastEmbedder`, which is what makes this tractable — the boundary already exists and `keel-core` deliberately cannot reach it.
  - `keel-daemon` decides whether embeddings are on, and `keel` needs one for `reembed`. Both would need the feature threaded, and `reembed` would have to say something honest when built without it rather than silently doing nothing.
  - Search already degrades rather than breaking, so the query path may need nothing.
  - The release matrix and `dist-workspace.toml` go back to three targets, and `--features` has to reach `dist build`, which is the part most likely to be awkward.
  
  Worth checking first, because it might make this unnecessary: whether a newer or older `ort` has a wider prebuilt matrix. `2.0.0-rc.13` is what `fastembed 5` pins, so that probably means moving `fastembed` too.
  
  Until this lands, §12 tier 2 cannot run at all — there is no Linux binary to put in the VM — so KEEL-219 is waiting on it.

- **KEEL-219** Stand up the Linux VM and run tier 2 for the first time `p2` · phase10, release, verification

  Split out of KEEL-210, which built both checks. Tier 1 is built and has run and passes 14 of 14. This is the half that needs hardware.
  
  **Why it cannot be done from the command line here.** The only Linux target is `x86_64-unknown-linux-gnu`. Docker on Apple Silicon gives arm64 Linux, and Linux ARM is deliberately not a target because there is no prebuilt ONNX Runtime for it. So there is no Linux binary this machine can execute, and no container trick that changes that. It needs an actual x86_64 Linux VM, which means an ISO, an installer that wants a screen, and a snapshot taken before anything is installed into it.
  
  **What it buys, and why the phase called it the highest value per unit of effort.** Linux is the one platform whose behaviour nothing here can predict. CI now compiles and tests on it, which is new as of 2026-08-14, but compiling is not running a release artifact. The check that only this can answer is the **glibc floor**: a binary linked against a newer glibc than the target distribution has does not degrade, it refuses to start, with a `GLIBC_2.xx not found` message that reads to a user like a corrupt download. `release.yml` builds Linux on `ubuntu-22.04` to keep that floor at 2.35. Nothing has ever confirmed the floor is where it was meant to be.
  
  It also covers the installer on a non-Mac, the systemd unit surviving a `SIGKILL`, and the corruption refusal through the other branch of the patched installer — coreutils has `sha256sum` and often no `shasum` at all, so Linux exercises the path macOS never takes.
  
  **Two things that will fail if it is run on the wrong machine, both correctly.** The toolchain check looks where Rust installs rather than stripping a `PATH`, so any host with cargo on it fails. The service check needs a user systemd bus, so a bare `ssh` exec fails. Both are deliberate: a check that reports green on a machine that could not answer it is what this tier exists to avoid, and it is why the script is not wired into CI — a GitHub Linux runner would go red on exactly those two.
  
  The artifacts to point it at come from a release build. Until there is a tag, that means copying `target/distrib` from a Linux CI run into the VM; afterwards it can install from the release itself, which is the mode worth running once as well.

- **KEEL-217** A task can be created directly in a terminal status, skipping the rule that guards closing one `p2` · mcp, storage

  Hit by doing it: KEEL-216 was created with `fields: {"status": "done"}` and landed as `status: done`, `close_reason: null`, `close_message: null`, `evidence: []`, `closed_at: null`.
  
  The standing contract says this is impossible: "A task cannot reach a terminal status without a reason, a message and — for `done` — evidence: the check is in the storage layer, so the CLI and MCP cannot disagree and moving the status by hand does not get round it."
  
  It is true of the path it guards. `update` computes `terminal` and calls `task.validate_close()` on the transition, and there is a comment explaining why it is on the transition and not on every write — a hundred and seven tasks predate the rule and checking always would freeze them. That reasoning is right. It just leaves the create path open, where there is no previous status to transition from.
  
  The consequence is a row that reads as finished and says nothing about why, which is precisely what the rule exists to prevent. It also has a null `closed_at`, so it is invisible to anything asking what was closed and when — including, probably, the changelog and any "what shipped this week" query.
  
  Two candidate fixes:
  
  1. **Refuse a create into a terminal status.** A task nobody ever opened did not happen, and back-filling history is what `keel import` is for. Simplest, and it makes the invariant structural.
  2. **Hold it to the same rule** — require reason, message and evidence when a create names a terminal status, and stamp `closed_at`. More permissive, and it keeps the door open for adopting a finished backlog.
  
  Recommending 1, with 2 as the answer if adoption turns out to need it. Either way `closed_at` must be stamped wherever a row reaches a terminal status, because a closed task with no closing time is a hole in the one log that is meant to be complete.
  
  Worth checking whether the same gap exists for the other statuses that have side effects, and whether `keel_create` should be refusing a `claimed_by` too.

- **KEEL-186** A running daemon blocks writes to stores it is not serving `p2` · cli, daemon

- **KEEL-184** Generated files and stored bodies differ by a trailing newline, so re-importing one is not a no-op `p2` · cli, storage

  Found by `keel import --dry-run` the first time it was pointed at real files, which is a decent argument for the flag.
  
  ```
  revise     product/SPEC.md  →  Keel — Technical Specification
  unchanged  product/PRD.md   →  Keel — Product Requirements Document
  unchanged  product/JOURNAL.md → Keel — Build journal
  ```

  ```
  store bytes : 68690    tail: 'rDB/falkordb-rs-next-gen)'
  disk  bytes : 68691    tail: 'DB/falkordb-rs-next-gen)\n'
  ```
  
  The stored body has no trailing newline and the generated file does. `body_hash` covers title and body, so that one byte is a different hash and the import would write a revision that changes nothing anyone can read.

Normalising on the way *in* — ensuring a stored body ends with exactly one newline — fixes it for every document and quietly rewrites one existing body. Writing the body verbatim on the way *out* leaves the file without a trailing newline, which most tools and every `diff` will complain about. The first is probably right, but it changes stored content, so it wants deciding rather than assuming.

Re-importing it now reports `unchanged`. That is one document out of 105 and it does not close this.  It also sharpens which fix is right. Normalising on the way in would rewrite 105 stored bodies — a revision each, all of them differing by one invisible byte, which is a lot of history for nothing anyone can read. Worth considering a third option the task did not list: normalise on *comparison* rather than on storage, so `body_hash` is computed over a body with trailing whitespace trimmed. That makes the round trip a no-op without rewriting anything, at the cost of two documents differing only in trailing whitespace being treated as the same document — which, for markdown, they are. - **KEEL-136** The pre-commit check reads the wrong tree from a git worktree `p2` · tooling

  Hit while committing KEEL-132 from `.claude/worktrees/competent-mayer-aa62e7`.
  
  `scripts/pre-commit` runs `keel generate "$project" --check` with no `--repo`, so the check resolves the project's recorded `root_path` — the main checkout. From a worktree the files being compared are not the files being committed.
  
  Both directions are wrong, and the second is the one that matters:
  
  - **False alarm.** Regenerating in the worktree left it clean, and the hook still reported `stale product/SPEC.md` because the main checkout has the old file. The commit went through with `--no-verify` after verifying by hand with `keel generate keel --repo "$PWD" --check`.
  - **False pass.** The same lookup means a genuinely hand-edited file in a worktree is compared against the main checkout's copy. If the main checkout happens to be current, the check passes and the edit is committed — which is the exact failure the hook was written to replace, since the mechanism it replaced was deleted for silently doing nothing.
  
  The fix is one flag: pass `--repo "$(git rev-parse --show-toplevel)"`, which is the tree the commit is in and equals `root_path` when there is no worktree. The header comment already argues at length that a check which cries wolf gets bypassed with `--no-verify`, and that this is the same disease as a hook that quietly does nothing. This is that, from a direction it did not anticipate.

  - The write side has the same bug, and it is worse than a false alarm. `keel generate` with no `--repo` also resolves `root_path`, so running it from a worktree writes into the main checkout — the files land as uncommitted changes on whatever branch that checkout has out, and `git status` in the worktree you ran it from says clean.  That happened here at 23:47, closing KEEL-133 from a worktree: five files written into the main checkout on `phase-9-one-database`, including the 649-line `product/SPEC.md` from your KEEL-132 work, which was in the store but not in that checkout. Reverted by hand with `git checkout --` plus an `rm` of the new decision file. Nothing was lost, because every one of them is a render of the store — but a session that did not think to look in the other tree would have left them there, and the next person to `git status` the main checkout would find a stranger's diff.  So `--repo "$(git rev-parse --show-toplevel)"` fixes the hook, and the same defaulting belongs in `generate` itself: when the command is run inside the project's repository, the tree you are in is the tree you mean. `--show-toplevel` gives the worktree root, which is the wanted answer in both cases.  KEEL-138 said this separately and is closed as a duplicate of this row.  *(Replaces a retracted note with identical content.
